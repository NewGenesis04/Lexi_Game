## 2026-06-05 — SSE reconnect race condition eliminated; blank tile handling fixed; game-adjust timer semantics adopted

### What was built

**1. SSE reconnect race condition diagnosed and fixed.**

The bug: when the browser's `EventSource` reconnects (which it does automatically on transient network errors), the *old* SSE connection's `finally` block fires, calls `disconnect_player`, marks the player disconnected, and pauses the game — all while the *new* connection is already being established. The new connection then arrives to find the game `PAUSED`, even though the player never actually left.

The fix spans five modules:

- **`frontend/src/composables/sse.ts:27-31`** — The `onerror` handler was previously calling `es.close()` + `setTimeout` + `connectSSE` to manually restart the connection. This was the root cause: closing the old `EventSource` triggers its `finally` block server-side, which runs `disconnect_player`. Since the browser's `EventSource` API already reconnects automatically on error, the manual reconnect is both redundant and harmful. The handler was reduced to a comment-only no-op.

- **`packages/backend-api/src/backend_api/game_manager.py:12`** — The connection map was redesigned from `_connected: dict[str, dict[str, bool]]` (code → player_id → True/False) to `_connections: dict[str, dict[str, set[str]]]` (code → player_id → set of tokens). This allows tracking multiple concurrent SSE connections per player token, which is essential because during a reconnect there is a window where both the old and new connections coexist. `mark_connected`/`mark_disconnected` were replaced with `add_connection(code, player_id, token)` / `remove_connection(code, player_id, token)` — the latter returns `True` when the player has no remaining connections.

- **`packages/backend-api/src/backend_api/game_manager.py:13`** — A new `_pending_disconnects: dict[str, dict[str, asyncio.Task]]` was added alongside `schedule_disconnect_check`/`cancel_disconnect_check` accessors. These manage per-player grace-period timers: when an SSE disconnects, a short timer (10 seconds) is created; if the player reconnects before it fires, the timer is cancelled.

- **`packages/backend-api/src/backend_api/services/game_service.py:247-390`** — `connect_player` and `disconnect_player` were rewritten. `disconnect_player` no longer pauses the game immediately. Instead, it calls `remove_connection`; if the player still has other connections, it returns early. Only when the last connection is removed does it schedule `_pause_after_grace` — a 10-second (cancellable) grace window before the game is actually paused. `connect_player` calls `add_connection` and `cancel_disconnect_check` to abort any pending grace timer, then resumes the game if both players are back. Both methods now accept a `token` parameter and silently return if the game doesn't exist (safe to call from the SSE generator's `finally` block).

- **`packages/backend-api/src/backend_api/routes/events.py:46-49,80-84`** — Both `connect_player` and `disconnect_player` calls in `_event_generator` were wrapped in try-catch to prevent exceptions from crashing the generator. The `connect_player` call was moved before the initial state load so that the `connected_map` in the emitted view reflects the current connection state.

**2. Blank tile handling corrected in `buildPlacePayload`.**

**`frontend/src/composables/usePendingMove.ts:20-35`** — The `buildPlacePayload` function was constructing `PlacedTileIn` objects where the `letter` field contained the user's chosen letter (e.g., `'A'`) instead of the blank sentinel `' '`. The server-side validator expects `letter: ' '` for blank tiles, with the chosen letter in `plays_as`. Fixed by sending `letter: isBlank ? ' ' : tile.letter` and `plays_as: isBlank ? chosen : null`.

**3. Auto-show blank picker on tile placement.**

**`frontend/src/components/game/GameBoard.vue:48-53`** — After placing a tile on the board, if the placed tile is a blank (detected via `ghostAt` and `ghostLetterAt` props returning `undefined`), the blank letter picker is automatically shown via `nextTick`. This prevents the UX dead-end where a player places a blank tile and then has to click it again to choose the letter.

**4. SSE stream connection moved from LobbyView to GameView.**

**`frontend/src/views/LobbyView.vue:17-32`** — The `store.connectSSEStream()` calls in `handleCreate` and `handleJoin` were removed. SSE connection is now established by `GameView` on mount, ensuring the stream is created only when the user enters the game page rather than during the redirect. This also means a game created/joined from outside the lobby path will still get an SSE stream.

**5. GC sweep hardened.**

**`packages/backend-api/src/backend_api/main.py:29-55`** — The 30-minute garbage-collection sweep for `PAUSED` games was hardened: it now acquires the per-game lock before loading state, uses `GamePhase.PAUSED` enum instead of the string `"paused"`, and calls `game_manager.remove_game(code)` to clean up runtime state (timers, locks, connection maps) before deleting the repo record.

**6. Tests updated for new API surface.**

**`packages/backend-api/tests/test_game_service.py`** — All `connect_player` and `disconnect_player` test calls updated to pass token parameters. `mark_connected`/`mark_disconnected` calls replaced with `add_connection`. A new regression test `test_disconnect_player_does_not_pause_if_player_never_connected` was added: if an SSE connection was established during `CREATED` phase (where `connect_player` returns early without marking the player connected), a subsequent disconnect must NOT pause the game. The existing `test_disconnect_player_pauses_playing_game` now fires the grace timer manually (`svc._pause_after_grace(code, pid, grace_secs=0)`) to verify the pause logic.

### Decisions taken

**Decision 1: Grace window (10s) rather than immediate pause on SSE disconnect.**

The original design paused the game as soon as `disconnect_player` was called. This was too aggressive: transient network blips (a Wi-Fi flutter, a proxy reconnecting, a browser tab coming back from background) would cause a false pause — both players see the game freeze for a few seconds and then unpause when the SSE reconnects. The 10-second grace window absorbs these transient disconnects without any visible state change. The window is short enough that a genuinely disconnected player still triggers the pause within a reasonable time. The player is still *marked* disconnected immediately (no tiles can be placed), but the game phase doesn't transition to `PAUSED` until the grace expires.

**Decision 2: Token-based multi-connection tracking rather than a single boolean per player.**

The original `_connected[code][player_id] = True/False` model assumed one connection per player. During a reconnect, the old connection's `finally` block runs `disconnect_player` before the new connection has called `connect_player`, so there is a window where the player goes from "connected" (old conn) to "disconnected" (old conn's `finally`) to "connected" (new conn). Using a set of tokens means both connections can be tracked simultaneously, and `remove_connection` only triggers the grace timer when the count drops to zero.

**Decision 3: Silence exceptions in SSE generator rather than crashing the stream.**

The `_event_generator` is a long-lived async generator. If `connect_player` or `disconnect_player` raises an exception (e.g., Redis is down), the generator would abort, closing the SSE stream and forcing the client to reconnect — creating a reconnection cascade. Wrapping the calls in try-catch means transient backend errors do not close the stream; the player simply gets stale state until the next broadcast.

### Problems identified

**Problem 1: `_connected` → `_connections` rename breaks any external code or scripts that imported the old attribute.**

*Location:* `packages/backend-api/src/backend_api/game_manager.py:12`

The internal dict was renamed from `_connected` to `_connections`. The module-level variable is private (underscore-prefixed), so only `test_game_service.py` accessed it directly (in the `clear_game_manager` fixture, now updated). No other consumers in the codebase reference it. *Closed.*

**Problem 2: No integration test for the reconnect-then-grace-cancellation path.**

The new `_pause_after_grace` method is tested indirectly by `test_disconnect_player_pauses_playing_game` (which fires it with `grace_secs=0`), but there is no test that simulates the full flow: SSE disconnects → grace timer starts → SSE reconnects → grace timer cancelled → game stays PLAYING. Writing this test would require either real `asyncio` sleeps (slow) or an injectable clock. *Open.*

**Problem 3: Race between `_pause_after_grace` and `_disconnect_grace_task` when both players disconnect in quick succession.**

If p1 disconnects, `_pause_after_grace` starts a 10s timer. Before it fires, p2 also disconnects. p2's `disconnect_player` sees the game is still `PLAYING`, so it schedules *another* `_pause_after_grace` for p2. When p1's timer fires, it pauses the game and spawns `_disconnect_grace_task`. Then p2's timer fires, sees the game is already `PAUSED`, and returns. The `_disconnect_grace_task` has already started its 5-minute countdown with only p2's token and no `connected` flag for p1 — this is the correct behaviour (the game should stay paused until one player returns), but the dual timers create unnecessary task overhead. A possible optimisation: check if a pause timer is already pending before scheduling a second one. *Open.*
