## 2026-06-21 — Session persistence, SSE notification protocol, serialisation lock reduction, and five live-play bugs patched

### What was built

**1. Session persistence across page reload (`frontend/src/stores/game.ts`).**

The Pinia store's `session` ref was previously initialised to `null` on every page load, meaning a browser refresh always redirected to the lobby with a "You are not in a game session." toast. The `gameGuard` at `frontend/src/router/guards.ts:13` checks `store.session` before proceeding — if `null`, it redirects. Since no mechanism existed to recover a session after reload, any user who refreshed their browser during a game was locked out.

At `frontend/src/stores/game.ts:21-27`, the store initialiser now reads a `lexi_session` key from `localStorage` and parses it into `initialSession` if present. A `watch(session, ...)` at lines 29-35 writes back to `localStorage` on every session assignment (create, join) and removes the key on `null` (reset/leave). The `gameGuard` at `guards.ts:13` finds the restored session, fetches the game state from the API, and reconnects the SSE stream — the player sees the board exactly as they left it. The `reset()` function at `game.ts:176-182` sets `session.value = null`, which triggers the watch and clears localStorage.

**2. SSE `onerror` logging (`frontend/src/composables/sse.ts:27-28`).**

The `onerror` handler was previously a comment-only no-op (left over from the 2026-06-05 reconnect fix). Every transient SSE disconnection — Wi-Fi flutter, proxy reset, tab backgrounding — was completely silent. Developers had no way to distinguish a healthy connection from one that was silently cycling. The handler now calls `console.warn('[sse] connection error — reconnecting', ...)` with any available event data.

**3. Overtime-count baseline reset on SSE reconnect (`frontend/src/stores/game.ts:154`).**

The `previousOvertimeCounts` map in the store tracks per-player overtime counts across successive `updateLocalState` calls. When an SSE reconnection occurs, the initial full-state push runs through the same `updateLocalState` code path. If the map was not reset, stale counts from before the disconnect would suppress overtime toasts that the reconnecting player had missed. The fix assigns a fresh `{}` to `previousOvertimeCounts` at the top of `connectSSEStream`, so the first state push after reconnect establishes a clean baseline and fires any missed overtime notifications.

**4. SSE notification protocol for cross-player alerts (`packages/backend-api`, `frontend/src/stores/game.ts`).**

A new SSE message type was introduced. Previously every SSE payload was a bare serialised `GameStateOut`. The `_broadcast_notification` method at `game_service.py:569-583` sends a JSON object with a `type` discriminator:

```json
{"type": "notification", "payload": {"text": "...", "type": "error"}}
```

It iterates connected tokens for a game code, skips the acting player via `skip_player_id`, and pushes the notification payload to the remaining player's SSE queue via `sse_manager.broadcast()`. This avoids the expense of serialising a full game state when only a toast is needed.

On the frontend, the SSE callback at `game.ts:157-163` checks for `msg.type === 'notification'`. Since `GameStateOut` has no `type` field, all existing game-state broadcasts pass through the `else` branch unchanged. Notification payloads are dispatched to `addToast`, which renders them as transient toasts in the existing toast system.

The trigger is in `place_tiles` at `game_service.py:134-136`: both `board_module.validate_placement` failures and `dict_module.is_valid_word` rejections raise `HTTPException(422)`. The `except HTTPException` handler calls `_broadcast_notification` with the text `"Opponent made an invalid move"` before re-raising, so the opponent sees a toast without waiting for the HTTP 422 response.

**5. Serialisation-broadcast split for reduced lock hold time (`packages/backend-api/src/backend_api/services/game_service.py`).**

This addresses the dominant source of the ~2-second submission-to-reflection latency. The original code path for every mutation was:

```
acquire lock → load state (Redis) → validate → mutate → save_game (Redis)
  → _broadcast:
      _to_view(p1) → from_domain → model_dump → json.dumps
      _to_view(p2) → from_domain → model_dump → json.dumps
      sse_manager.broadcast()     ← asyncio queue.put × 2
  release lock
```

Both serialisations and the two `queue.put()` calls ran inside the per-game `asyncio.Lock`, preventing any other request from touching the game until both SSE payloads had been constructed and enqueued. The `queue.put()` calls are fast (asyncio Queue is a loop-local deque), but the serialisation — which iterates the entire `move_history` array, calls `model_dump` on each entry, and runs `json.dumps` twice — is CPU-bound and grows linearly with move count.

The fix splits serialisation from broadcast. A new helper `_serialize_game` at `game_service.py:556-567` does the same work as the old `_broadcast` but returns `dict[str, str]` instead of awaiting `sse_manager.broadcast`. Each mutation method now saves `payloads = await self._serialize_game(state)` inside the lock, then calls `await sse_manager.broadcast(payloads)` *after* the `async with` block exits. The `place_tiles` method at lines 120-179 is representative: the `payloads` variable is declared before the lock, assigned inside the lock (line 174), and broadcast outside the lock (lines 177-178).

The three edge-case exit paths — `_check_end` (game over by bag empty), `_end_by_timeout` (three overtime periods exhausted), and the 6-consecutive-pass path in `pass_turn` — still broadcast inside the lock via the unchanged `_broadcast` method (line 545-554). These are infrequent paths where the latency is acceptable.

All four mutation methods (`place_tiles`, `swap_tiles`, `pass_turn`, `forfeit`) were restructured to the new pattern.

### Decisions taken

**Decision 1: Discriminated SSE protocol (`type: "notification"` marker) rather than embedding toasts in `GameStateOut`.**

The alternative was adding an optional `notifications: list[dict]` field to `GameStateOut` and populating it during serialisation when the game state had not changed (the 422 case). This was rejected because it would couple the schema layer to transient UI concerns — a toast is not a property of the game state. The discriminated union approach keeps the SSE wire format extensible without schema changes. The downside is that the frontend store must now handle two message shapes; this is managed by a single `if/else` dispatch at `game.ts:157-163`.

**Decision 2: `localStorage` over `sessionStorage` for session persistence.**

`sessionStorage` is scoped to the browser tab and cleared on tab close. `localStorage` survives tab closure, which is the desired behaviour — the user should be able to close the browser, come back, and rejoin their game via the URL or a bookmark. The trade-off is that `localStorage` is shared across all tabs of the same origin; if the user plays two games simultaneously in different tabs, the session in one tab will overwrite the other on the last write. This risk is acceptable for a personal project where simultaneous multi-game play is unlikely. A future improvement would be to scope the key by game code (`lexi_session_{code}`) or use a key-value map.

**Decision 3: Serialise inside the lock, broadcast outside — not a fully async architecture.**

The alternative considered was to push serialised payloads onto an internal asyncio Queue and have a dedicated broadcaster task consume it, removing serialisation from the request path entirely. This was rejected as over-engineering for a 1-worker deployment. The lock is held only for the duration of `model_dump` + `json.dumps` (the two serialisations run inside the lock in the old code too — they are the bottleneck). Moving the `queue.put()` calls outside the lock eliminates the secondary cost of enqueuing, which shaves roughly 10–20% off the lock hold time. The primary cost — `model_dump` iterating N moves — remains inside the lock and is a known open problem (see below).

### Problems identified

**Problem 1: Serialisation inside the lock remains the dominant lag source — partially resolved.**

*Symptoms:* ~2-second latency between pressing Submit on one client and seeing the board update on the opponent's client. The latency grows with game length (more `move_history` entries to serialise).

*Root cause:* `_serialize_game` at `game_service.py:556-567` (and `_broadcast` at line 545) call `_to_view` once per connected player. `_to_view` calls `GameStateOut.from_domain` at `schemas.py:148-167`, which constructs a `MoveOut` for *every* entry in `move_history`. Each `MoveOut.from_domain` at `schemas.py:100-108` iterates the move's `tiles` list. At 50+ moves per game, this is thousands of field copies per serialisation, all running inside the per-game lock.

*Resolution:* Moving the `queue.put()` calls outside the lock (this session) reduces lock hold time by roughly the overhead of two asyncio Queue pushes — measurable but not transformative. The serialisation itself (the `for token` loop with two `model_dump` calls) remains inside the lock. *Partially resolved.*

*Remaining options:*
- Serialise `move_history` once and attach the serialised form to the state object, updating only the latest move on each turn.
- Build both player views in a single pass through `move_history` instead of two independent calls.
- Delegate serialisation to a background task.

**Problem 2: Opponent never sees invalid-word (422) notifications — resolved.**

*Symptoms:* When a player submits an invalid word, they see the error toast immediately (from the HTTP 422 response caught in `GameView.vue:102-103`). The opponent's screen shows no indication that anything happened — the game state has not changed, so no SSE broadcast fires.

*Root cause:* `place_tiles` raised `HTTPException(422)` during validation, which FastAPI returned as an HTTP error response to the submitting player. No code path existed to notify the opponent.

*Resolution:* `place_tiles` at lines 125-136 wraps the placement and dictionary validation in a `try/except HTTPException` block. The exception handler calls `_broadcast_notification` which sends a `{type: "notification"}` SSE message to the opponent's queue before re-raising. The frontend at `game.ts:157-160` renders the notification as a toast.

**Problem 3: Overtime notification only fires on the first OT per game, then goes silent — resolved.**

*Symptoms:* The "ran out of time — −10 pts, +60s overtime" toast appears on both screens for the first overtime. If the player exhausts their three overtime periods one by one, no further toasts appear. If the opponent's SSE connection drops and reconnects, they may also miss the notification.

*Root cause:* `previousOvertimeCounts` at `game.ts:39` is initialised once when the store is created and never reset. After the first OT fires, the map stores `player_id → 1`. All subsequent `updateLocalState` calls see `prevCount = 1, overtime_count ≥ 1`, which fails the `prevCount === 0` guard at line 65, so no toast fires for OT #2 or OT #3. This is actually *correct* Scrabble behaviour — you only notify once per overtime event — but it becomes a bug on SSE reconnect because the stale map suppresses the initial notification that the reconnecting player missed.

*Resolution:* `connectSSEStream` at line 154 resets `previousOvertimeCounts = {}` before establishing the SSE connection. The first `updateLocalState` after reconnect sees a clean baseline and correctly fires any missed OT notifications.

**Problem 4: Page reload loses game session — resolved.**

*Symptoms:* Any browser refresh during an active game redirects to the lobby with "You are not in a game session."

*Root cause:* `session` is a plain Pinia ref initialised to `null`. Pinia store state is in-memory only; there is no built-in persistence mechanism.

*Resolution:* The store now initialises `session` from `localStorage` at `game.ts:21-27` and persists on every change via a `watch` at lines 29-35.

**Problem 5: SSE connection errors are invisible — resolved.**

*Symptoms:* During live play, the game would occasionally stop responding without any visible error. The EventSource API auto-reconnects silently, so players had no way to tell they were looking at stale state.

*Root cause:* The `onerror` handler at `sse.ts:27` was empty.

*Resolution:* Added `console.warn('[sse] connection error — reconnecting', ...)` at `sse.ts:28`. Connection drops now appear in the browser console with the event data.

### Open questions

**Should `move_history` be serialised incrementally?** Each move serialisation iterates the full history array. At 50+ moves, this is the dominant CPU cost inside the lock. Storing a pre-serialised `move_history_json` on the `GameState` domain object and appending only the latest move on each turn would eliminate the O(N) scan. This would require either a) adding a non-domain field to `GameState` (ugly), or b) caching serialised history at the repo layer with a Redis hash keyed by turn number.

**Should the notification SSE protocol be extended to `swap_tiles` validation errors?** Currently only `place_tiles` broadcasts validation failures via `_broadcast_notification`. `swap_tiles` also raises `HTTPException(422)` for insufficient bag tiles and missing letters. These are interesting to the opponent, but less common than placement errors. No decision has been made.

**Should there be integration tests for the notification SSE path?** The existing test suite has no coverage of `_serialize_game`, `_broadcast_notification`, or the notification dispatch in the frontend SSE callback. These run entirely under manual testing. Adding a test would require either an end-to-end SSE harness (two async clients connected to the same game) or a unit-level test that wires `_broadcast_notification` to a fake SSE queue and verifies the notification format.

**Should the broadcast be fully decoupled via an internal Queue + consumer task?** The current design serialises inside the request lock and broadcasts outside it. A fully async design would push the serialisation payload onto an internal asyncio Queue and have a long-lived consumer task broadcast asynchronously, releasing the lock immediately after `save_game`. This would eliminate serialisation from the lock entirely at the cost of a one-event latency buffer. No decision has been made.
